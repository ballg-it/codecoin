`.bet-btn small` = **10.5px** (Sarabun) — เล็กสุดในเกม, รองลงมาคือ 11px (`.menu-item small`, `.footer-note`) และ 11.5px (`.player-btn`, fatalDetail inline)
ทั้งหมดเป็น label รอง ไม่ใช่เนื้อหาคำถาม/คำตอบหลัก (เนื้อหาหลักอยู่ที่ 14–15px) — แต่ 10.5px บนมือถือจริงถือว่าเล็กมาก โดยเฉพาะกับฟอนต์ไทยที่มีวรรณยุกต์/สระซ้อน

### 3.4 Safe-area (iPhone notch) และจอแคบ 360px

- **ไม่มี `viewport-fit=cover`** ใน `<meta name="viewport">` (บรรทัด 5) และ **ไม่มีการใช้ `env(safe-area-inset-*)` เลยทั้งไฟล์**
- ปุ่มลอย 4 ปุ่ม (`.mute-btn`, `.motion-btn`, `.player-btn`, `.net-badge`) ใช้ `bottom:14px`/`right:14px`/`left:14px` แบบ fixed px ล้วน — บน iPhone ที่มี home-indicator (ไม่มี viewport-fit=cover ระบบจะไม่ยอมให้เนื้อหาล้ำเข้าไปในเขต inset เองอยู่แล้ว ดังนั้นในทางปฏิบัติปุ่มจะไม่โดนแถบขาวทับ) — **ความเสี่ยงจริงคือกลับกัน**: เพราะไม่ประกาศ `viewport-fit=cover` เนื้อหาจึงถูกบีบเว้นระยะจากขอบจอเสมอ (ปลอดภัยแต่เสียพื้นที่จอเล็กนิดหน่อย) ไม่ใช่บั๊กบัง UI — บันทึกไว้เป็นระดับสังเกตการณ์ ไม่ใช่จุดต้องแก้ด่วน
- จอ 360px: `.app{max-width:430px}` ยืดหด 100% ปกติ, `.roulette-wheel-wrap` คงที่ 168×168 (พอดีสบายในจอ 360), `.rescue-input`/`.rescue-code` มี `letter-spacing:8px` ที่ font-size 26–34px — กับรหัส 4 ตัวอักษรคำนวณกว้างประมาณ 110-150px ยังพออยู่ในจอ 360 ได้สบาย ไม่พบจุดล้นจอที่ชัดเจนจากการอ่านโค้ด (ควรวัดจริงบนอุปกรณ์เพื่อความชัวร์ 100% เพราะไม่ได้รันเบราว์เซอร์ตรวจในรอบนี้)

## 4. ไล่ทุก route แล้วบอกว่าหน้าไหนหลุดจากหน้าอื่น

รายชื่อฟังก์ชัน render ทั้งหมดในไฟล์ (29 ฟังก์ชัน):

`renderPlayerGate · showNotFound · showFatal · renderSpace · renderUpgrade · renderEvent · renderSpeedEvent · renderBugjam · renderBugQuestion · renderQuestion/MCQ/Hotspot/ColorWheel/LinePick · renderQuiz · renderMenu · renderRescueLanding/Solver/Guide · renderDebugRescue · renderCoolingBoss · renderMeltdownJoin/Ready/Fight/Summary · renderCoolingWirecut/Ready/Play · renderBankPanel · renderRescanGate`

**หน้าที่หน้าตาสอดคล้องกันดี:** ทุกหน้าใช้ `.card` + `.zone-tag` + `h2` + `.content` เป็นโครงร่วม ไม่มีหน้าไหนที่ทิ้งโครงนี้ไปทำ layout แปลกใหม่เอง

**จุดที่ "หลุด" หรือควรสังเกต:**

1. **สี zone-tag ของ Cooling Zone / Server Meltdown ใช้ hex ดิบ `#38BDF8` ซ้ำ 8 จุด** (renderCoolingBoss, renderMeltdownJoin/Ready/Fight/Summary, renderCoolingWirecut/Ready/Play) แทนที่จะใช้ `var(--office)` — ผลลัพธ์ภาพเหมือนกันเป๊ะ (เพราะค่าเท่ากัน) แต่ **ถ้าใครวันหลังไปแก้ `--office` ที่เดียวใน `:root` หน้ากลุ่ม Cooling/Meltdown 8 หน้านี้จะไม่ตามการเปลี่ยนสีไปด้วย** ทั้งที่แนวคิดคือ "Cooling Zone = โซน office" นี่คือจุดที่ผิดหลักการ token มากที่สุดในไฟล์
2. **`renderRescueLanding()` ใช้ zone-tag สีแดง (`var(--bad)`) กับข้อความ "🚨 Server Error"** — สีแดงในทุกหน้าอื่นของเกมสื่อถึง "ตอบผิด/พลาด/เสียเงิน" (`.choice.wrong`, `.result.lose`, `.lockout`) แต่ที่นี่ใช้เป็น **ธีมตกแต่งของมินิเกม** (สมมติว่าเซิร์ฟเวอร์ error จริง ๆ ในเนื้อเรื่อง) ไม่ใช่การแจ้ง error ของระบบเว็บจริง — จงใจแยกความหมายจาก `showNotFound()`/`showFatal()` ที่ก็ใช้สีแดงเหมือนกันสำหรับ error จริง คนละบริบทแต่ใช้สีเดียวกัน อาจทำให้ผู้เล่นเข้าใจผิดว่าเว็บพัง ทั้งที่จริง ๆ คือหน้าเปิดมินิเกมปกติ — ควรพิจารณาว่าจงใจหรือไม่ (ไม่ใช่บั๊ก แต่เป็นจุดกำกวมด้าน UX สี)
3. **หน้า renderMenu()** มีของตกแต่งเพิ่มเข้ามาคนละชุดกับหน้าอื่น (ภาพ SVG แผงวงจร, hex ดิบเยอะมาก ~25 ค่าเฉพาะจุดนี้) — เข้าใจได้ว่าเป็นภาพประกอบหน้าแรกจึงยอมให้ "หลุด" จาก token ปกติได้ (ไม่กระทบ readability เกม)
4. **หน้า error (`showNotFound`/`showFatal`) และหน้าทดสอบ (`renderRescanGate`)** ใช้โครง `.card`+`.zone-tag` เดียวกับหน้าเกมปกติ ไม่หลุด — ดีแล้ว
5. **ปุ่ม "กลับเมนู" ท้ายหน้า `renderRescueGuide`** (บรรทัด 2830) มี inline `style="margin-top:14px;"` เฉพาะจุดเดียวในไฟล์ที่ปุ่ม `.btn` ธรรมดาต้องพ่วง margin เพิ่มเอง — ทุกที่อื่น `.btn` ใช้ `margin-top:10px` จาก class เดิมพอ จุดนี้เป็น one-off (ต่ำ, ไม่กระทบสายตา)

## Stage V3b — ปิดงาน 2 จุด + แก้ไขกฎสี + บันทึกเรื่องค้าง

### ปัญหา

รอบ V3 พบ 3 จุดที่ยังใช้ `var(--bad)` แดงบน zone-tag นอกเหนือ `showNotFound`/`showFatal` แต่ยังไม่ได้ตัดสินว่าควรแก้หรือไม่ รอบนี้ตัดสินแล้ว: `renderRescueSolver()` ต้องแก้ (สับสนกับ error จริงเหมือนกรณี landing) ส่วน `renderBugjam()`/`renderBugQuestion()` **ไม่แก้** เพราะเป็นสถานะ "ผู้เล่นกำลังโดนลงโทษ/ติดบั๊กในเกม" (penalty state ของมินิเกม) ไม่ใช่ "ระบบเว็บมีปัญหา" — ต่างจาก debug_rescue landing ตรงที่ผู้เล่นเพิ่งเข้าเกมนี้ครั้งแรก ยังไม่รู้บริบท จึงเข้าใจผิดว่าเว็บพังได้ง่ายกว่า ในขณะที่ bugjam แดงคือส่วนหนึ่งของกติกาเกม (ชื่อหน้าก็บอกอยู่แล้วว่า "ติดบั๊ก") ผู้เล่นรู้บริบทตั้งแต่เข้าเกมแล้ว

### แก้ 2 จุด

1. `renderRescueSolver()` zone-tag: `var(--bad)` → `var(--gold)` (ให้ตรงกับ `renderRescueLanding()`/`renderRescueGuide()` ที่เป็นมินิเกมเดียวกัน) — ข้อความ "🖥 ผู้กด · รหัส..." **ไม่แตะ** ยังใช้แยกบทบาทได้เหมือนเดิม ([index.html:2799](../index.html))
2. `renderRescueLanding()` บรรทัดชี้แจง: อิโมจิ ⚠️ (สัญลักษณ์เตือนภัย ขัดกับใจความ "เว็บทำงานปกติ") → ℹ️ (สัญลักษณ์ข้อมูล) ([index.html:2747](../index.html))

### กฎสีฉบับแก้ไข

> **`var(--bad)` (แดง) = แย่สำหรับผู้เล่น** เท่านั้น — เว็บพังจริง (`showNotFound`/`showFatal`) หรือ ติดบั๊ก/ตอบผิด/ถูกล็อกในเกม (`renderBugjam`/`renderBugQuestion`/`.choice.wrong`/`.result.lose`/`.lockout`)
> **ห้ามใช้ `var(--bad)` เป็นสีบรรยากาศของเนื้อเรื่อง** (เช่น "รีบด่วน!" "เร่งมือ!") ที่ไม่ได้แปลว่าผู้เล่นกำลังแย่จริง ๆ — กรณีนี้คือที่มาของปัญหา `renderRescueLanding`/`renderRescueSolver` ที่เพิ่งแก้ไป (ข้อความ "Server Error"/"🖥 ผู้กด" ใช้แดงเป็นบรรยากาศตื่นเต้น ทั้งที่ผู้เล่นยังไม่ได้ทำอะไรผิด/แพ้อะไรเลย)

### เรื่องที่ 2 — `colorVar()` ใน rAF loop กระทบ Motion Stage 5: **ไม่กระทบ (อ่านโค้ดยืนยันแล้ว), วัด fps จริงไม่ได้ในเครื่องมือทดสอบนี้**

**อ่านโค้ดทั้ง 2 จุดที่เกี่ยวกับวงล้อ Roulette:**
- `buildRouletteWheelSvg()` ([index.html:1614](../index.html)) เรียก `colorVar("--surface-deep")` **ครั้งเดียวตอนสร้าง SVG** (ก่อนเริ่มหมุน) — มีคอมเมนต์ในโค้ดต้นฉบับกำกับไว้ชัดเจนอยู่แล้วว่า "ห้ามวาด wedge ใหม่ทุกเฟรม ไม่งั้น CPU throttle 4x จะตกต่ำกว่า 50fps แน่นอน" (บรรทัด 1612) — ยืนยันว่าเป็นการออกแบบตั้งใจไว้แต่แรก ไม่ใช่บั๊ก
- `spinRouletteWheel()`'s `step()` loop ([index.html:1659](../index.html)) ที่ทำงานทุกเฟรมจริง **เรียกแค่ `paint(deg)` ซึ่งเป็น `wheelG.style.transform = ...` ล้วน ๆ** ไม่มี `colorVar()`/`getComputedStyle()` แม้แต่ครั้งเดียวในลูป
- ไล่ดู `colorVar()` ทุกจุดที่เรียกทั้งไฟล์ (6 จุด: 1350, 1619, 2285, 2306, 2344, 2376) — ครบทุกจุดเป็น one-shot ตอน build SVG หรือใน click handler ที่ทำงานครั้งเดียวต่อการแตะ ไม่มีจุดไหนอยู่ใน rAF loop เลย

**พยายามวัด fps จริงแล้วแต่เครื่องมือนี้ทำไม่ได้:** เบราว์เซอร์อัตโนมัติที่ใช้ทดสอบ (Claude Browser pane) รายงาน `document.hidden=true` ตลอดแม้ front tab แล้ว และแม้ override `document.hidden` เป็น `false` ผ่าน `Object.defineProperty` แล้ว requestAnimationFrame ก็ยังถูก throttle ระดับเบราว์เซอร์ (วัดได้ 1 เฟรมใน 4.7 วินาที) เพราะแท็บไม่ได้ render จริงบนหน้าจอ — เป็นข้อจำกัดของเครื่องมือทดสอบอัตโนมัติ ไม่ใช่บั๊กของเว็บ

**สรุป:** จากการอ่านโค้ด **ยืนยันได้ 100% ว่า `colorVar()` ไม่ได้ทำงานทุกเฟรม** จึงไม่กระทบ fps ของ Motion Stage 5 ตามที่กังวล — แต่ตัวเลข fps จริงบนอุปกรณ์จริงยังไม่ได้วัด (ต้องใช้ Chrome DevTools Performance panel บนอุปกรณ์จริง/เบราว์เซอร์จริงที่ไม่ถูก throttle ถ้าต้องการตัวเลขยืนยันเชิงประจักษ์)

### เรื่องที่ 3 — V2b กริด 2×2 แก้ปัญหา 796px ได้ไหม: **มีคำตอบอยู่แล้วใน DESIGN_AUDIT.md ตั้งแต่ Stage V2b — เป็นการเข้าใจผิดตอนเขียนสรุป V3**

ตรวจสอบพบว่าเรื่องนี้ **ถูกวัดและบันทึกไว้ครบถ้วนแล้วตั้งแต่ Stage V2b** (ดูหัวข้อ "FIX-1b" ด้านบนในไฟล์นี้) การใส่ไว้ในรายการ "เรื่องค้าง" ของ V3b เป็นการเข้าใจผิด/รายงานซ้ำโดยไม่จำเป็น — ขอแก้ไขตรงนี้:

- ไล่วัดครบทั้ง 76 คำถามที่เป็นไปได้ในคลัง `event_coding` mechanic=speed แล้ว: **best-case 704.1px→647.1px (ผ่าน ≤700), worst-case 796.1px→739.1px (ยังเกิน 39px)**

- อีก 13 คำถามที่ยาวสุด (86–131 ตัวอักษร) ยังเกิน — สาเหตุเชิงโครงสร้างคือปุ่ม/ตัวเลือกที่ห้ามลดขนาด + ข้อความยาวจาก `data.json` ยังกินพื้นที่รวมเกิน 700px แม้ตัด header (101px) และใช้กริด 2×2 แล้ว (กริดคืนความสูง 55px แต่ตัวเลือกคำตอบยาวยังกิน 204px)

**สรุป:** ปิดเรื่องนี้ได้ — คำตอบคือ "กริด 2×2 แก้ได้ 83% ของคำถามที่เป็นไปได้ ส่วน 13 ข้อที่เหลือติดเพดานโครงสร้าง (ข้อความยาว+ปุ่มห้ามลดขนาด) ซึ่งเกินสโคปการบีบ margin/padding แล้ว ต้องแก้ที่ความยาวคำถามใน data.json หรือ redesign เลย์เอาต์แทน" — ไม่ใช่เรื่องที่ยังไม่ได้ตรวจตามที่เข้าใจผิดไว้
